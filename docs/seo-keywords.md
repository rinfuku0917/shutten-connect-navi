# SEOキーワード管理表（出店コネクトナビ）

このファイルはコネクトナビのSEO記事量産・カテゴリページ設計の設計図。
記事作成やカテゴリページ実装の際は必ずこのファイルを参照すること。

## 運用ルール

- 着手順はカテゴリ優先度順：**B → D → C → F → E → A → G**
- 記事を書いたら該当行のステータスを更新する（未着手 → 執筆済 → 公開済）
- 誘導先の種別：
  - **会員登録**：記事末尾のCTAを出店者登録 or 募集者登録に
  - **カテゴリページ**：/places/category/[tag] への内部リンクを主導線に
  - **案件一覧**：/places（都道府県絞り込み）への内部リンクを主導線に
- 1記事1キーワード。3,500〜4,500字。一次情報（実際の書類審査・手数料運用の実例）を必ず入れる
- 禁止：「いかがでしたか」等の常套句、根拠のない統計数値の創作

## 記事執筆時の共通テンプレート

Claude Code への記事作成指示は以下の型を使う：

```
このファイル（docs/seo-keywords.md）の未着手キーワードから優先度順に1本書いて。

- 構成：結論先出し → 本文（キーワードの検索意図に沿った実用情報）→
  必要書類や手数料など当プラットフォームの一次情報 → コネクトナビへの誘導（誘導先列に従う）
- 文字数：3,500〜4,500字
- h1は記事タイトル1つ。h2/h3の階層を守る
- 記事下の「関連する出店場所」枠に対応する都道府県 or カテゴリを設定
- 必ず入れる一次情報：書類審査で実際に求めている書類（営業許可証・PL保険・検体検査）、
  歩合/固定が現場ごとに異なる実例（施設名は伏せる）
- 禁止：「いかがでしたか」等の常套句、根拠のない統計数値の創作、競合の誹謗
- 書き終えたらこのファイルのステータス列を「執筆済」に更新する
```

### 記事を公開したあとに必ずやること

公開してから検証にかけたところ、2回とも実際の誤りが見つかった。
**書いた本人とは別の方法で数え直す工程を必ず入れること。**

とくに次の3種類を間違えやすい。
1. **自社の仕様を「たぶんこうだろう」で書く。**
   「応募には書類が必要」と書いたが、応募処理は書類を一切見ていなかった。
   サービスの動きを書くときは、必ずコードを読んで確かめる
2. **集計の母数を混ぜる。**
   固定額の集計に併用案件を混ぜ、歩合の最低保証額を「固定の下限」として出していた。
   何を数えたのかを記事本文にも書くこと
0. **自分が入れた変更が、別の画面を壊していないか確かめる。**
   profiles の閲覧を絞ったとき、募集者ダッシュボードだけ切り替え漏れがあり、
   募集者から応募者の名前が「(出店者)」に見える状態が続いていた。
   同じテーブルを使っている画面を全部洗い出すこと
3. **絞り込んだ集合の性質を、集合全体の性質として書く。**
   「平日が安い25件」を数えたのに「両方書かれた案件は全件で平日が安い」と書いた。
   実際は38件あり、13件は同額だった。**その25件は差があるものだけを集めた集合**で、
   「全件で差がある」のは当たり前。数えたあとに「この条件で絞ったから、
   こう言えるのは当然ではないか」と一度疑うこと。
   あわせて、**同じ会社の系列店が多数を占めていないか**も見る
   （平日の差額の中央値は、16件の同一系列が決めていた）
4. **「Aだけが特殊」と書く前に、B・Cも数える。**
   「スーパーだけ固定制に偏っている」と書いたが、商業施設も固定寄りで、
   偏っていたのは学校（30件すべて歩合）だった。
   比較の相手を数えずに「だけ」と書かない
5. **金額は「誰が払う額」か「誰が受け取る額」かを必ず書く。**
   募集要項の金額は出店者が払う総額で、場所側の受取ではない。
   募集者向けの記事で取り違えると、期待値を5割ふくらませることになる

  この4本が常時張られる。呼びたい方の列にエリア別4本があるのに出したい方の列には無い
  非対称を埋めたもので、意図してそうしている。
  1系統に戻すなら、`app/places/SegmentPage.tsx` と `app/vendor/area/[pref]/page.tsx` の
  本文の相互リンクを落として「フッターだけ」に寄せるか、`/vendor` 配下でフッターの列を出さない
  条件を入れる。**どちらを正とするかは運営の判断が要る。**
